# PR draft #1 — Better error when `auth/login` succeeds but no `ProjectMembership` exists

## Problem

When a `User` row exists with a valid password, but no `ProjectMembership`
links them to any Project, `POST /auth/login` returns:

```
401 Unauthorized
{ "outcome": { "issue": [{ "code": "invalid", "details": { "text": "User not found" } }] } }
```

The literal `"User not found"` string is **misleading** — the user exists.
What's missing is the membership. The lookup happens after a successful
password compare, but the error is generated by code that doesn't
distinguish "no `User` row" from "`User` row with empty membership list".

We hit this in production when a `ProjectMembership` row got accidentally
deleted while the `User` row stayed. The auth response made us spend ~30
minutes hunting "missing user" before realising the actual problem was
membership integrity.

## Why it matters

- Operators who restore from backups partially.
- Multi-tenant platforms where a project is unsubscribed but the underlying
  user account stays.
- Any debugging of auth issues — the current message actively misleads.

## Proposed fix

Differentiate the two failure modes in the auth handler:

```diff
- // packages/server/src/auth/login.ts (around the membership lookup)
- if (!user) {
-   throw new OperationOutcomeError(badRequest('User not found'));
- }
- const memberships = await getMembershipsForUser(user.id);
- if (!memberships.length) {
-   throw new OperationOutcomeError(badRequest('User not found'));
- }
+ if (!user) {
+   throw new OperationOutcomeError(badRequest('Email or password is invalid'));
+ }
+ const memberships = await getMembershipsForUser(user.id);
+ if (!memberships.length) {
+   throw new OperationOutcomeError(badRequest(
+     'User has no project memberships. ' +
+     'Contact a project admin to be re-invited.'
+   ));
+ }
```

Bonus: rename the "User not found" message to "Email or password is
invalid" everywhere it appears for genuinely-bad-creds — small but reduces
information leakage about which email addresses are registered.

## Files touched (rough estimate)

- `packages/server/src/auth/login.ts`
- `packages/server/src/auth/__tests__/login.test.ts` (add two new cases)

## Tests we'd add

- `auth/login → 400 with "no project memberships" when User exists, password matches, but no ProjectMembership rows`
- `auth/login → 400 with "Email or password is invalid" when User does not exist (instead of leaking existence)`

## Open questions

- Is the existing message wording deliberate (anti-enumeration)? If so, the
  no-membership case still needs to be distinguishable post-auth, just not
  pre-auth.
- Whether the no-membership error code should be `forbidden` (403) rather
  than `invalid` (400) — semantically it's "you authenticated, but you have
  no scopes here".
